# Тестовые данные и прохождение workflow в SwiftReview

Документ описывает данные из [seed-test-data.sql](../backend/scripts/seed-test-data.sql)
и ручные проверки назначения, подтверждения и Undo. В каждом сценарии указаны
пользователи, сообщение и ожидаемый результат. Это демонстрационные процессы с одним,
двумя и тремя этапами; привязки к типам сообщений и подразделениям не являются
утверждённой производственной матрицей.

## Подготовка базы и вход

1. Примените актуальные миграции, включая `AddWorkflowUndoPolicy`, по
   [инструкции backend](../backend/README.md). Остановите приложение и другие процессы,
   записывающие данные, перед загрузкой seed.
2. Выполните весь `backend/scripts/seed-test-data.sql` в выбранной тестовой БД.
   **Скрипт удаляет все существующие данные приложения, включая пользователей и аудит.**
   Схема и история миграций сохраняются. Не используйте рабочую БД для этих сценариев.
3. Убедитесь, что скрипт сообщил о 5 пользователях, 3 workflow и 75 сообщениях.
   В конце он выводит таблицы политик и пользователей. Отдельный скрипт настройки Undo
   и ручная выдача прав после seed не нужны.
4. Запустите приложение. В локальном Docker-окружении используется `./run-dev.docker.sh`,
   в Windows с внешним SQL Server — `./run-dev.ps1`. Загрузка seed выполняется отдельно
   от запуска приложения.

В режиме `Development` выберите пользователя через параметр `user` в адресе браузера.
Например, `http://localhost:5173/messages/assigned?user=theo.mercer` открывает очередь
проверки от имени Theo. Это механизм тестового входа; пароли для этих пользователей
вводить не требуется. Без явного выбора можно оказаться под `admin`, поэтому всегда
проверяйте имя текущего пользователя.

Удобно открыть отдельную вкладку для каждого пользователя. Параметр сохраняется
в `sessionStorage` вкладки. После действия другого пользователя нажимайте **Refresh**:
таблица в соседней вкладке сама по себе не обязана обновиться.

## Пользователи и права

| Имя в интерфейсе | Пользователь | Область доступа | Назначение в сценариях |
|---|---|---|---|
| Amelia Hart | `amelia.hart` | Только London / CS | Один этап и проверка ограничений области |
| Theo Mercer | `theo.mercer` | Все 3 филиала и 3 подразделения | Назначение, Undo чужого первого подтверждения, третий этап |
| Priya Nair | `priya.nair` | Все 3 филиала и 3 подразделения | Первый проверяющий, отмена собственного подтверждения |
| Lucas Bennett | `lucas.bennett` | Все 3 филиала и 3 подразделения | Второй проверяющий |
| Administrator | `admin` | Глобальный доступ | Проверка административного исключения |

Четыре обычных пользователя имеют роль `Reviewer`: просмотр, назначение, проверка
уровней 1–3, `review.undo` и просмотр аудита в своей области доступа. Они не могут
управлять workflow или открывать администрирование. Роль `Operations manager` у `admin`
содержит все права; глобальные исключения определяются также отдельным признаком
администратора.

Полезные адреса, где вместо `USERNAME` нужно подставить имя пользователя из таблицы:

- Назначение: `http://localhost:5173/messages?user=USERNAME`.
- Проверка и Undo: `http://localhost:5173/messages/assigned?user=USERNAME`.
- Администрирование: `http://localhost:5173/admin?user=admin`.

## Состав сообщений и политики

В seed есть филиалы London, Dublin, Singapore и подразделения CS, TFO, DC.
Каждый workflow содержит 25 сообщений, распределённых по трём филиалам. Всего
75 сообщений с номерами `TEST-00001`–`TEST-00075`. Время получения находится в последних
75 часах; текст сообщения содержит название демонстрационного сценария.

После загрузки все сообщения имеют состояние `New`, без исполнителя и попыток проверки.
В аудите каждого сообщения есть `MessageRegistered`. Числовые ID генерирует SQL Server,
поэтому в ручных сценариях ищите сообщение по **External ID**, а не по ID строки БД.

| Workflow | Тип и подразделение | Обязательные этапы | Undo обычного пользователя |
|---|---|---|---|
| Single confirmation - no undo | MT199 / CS | 1 | Запрещён |
| Two confirmations - undo first | MT299 / TFO | 1, 2 | Последнее нефинальное подтверждение может отменить любой уполномоченный пользователь; активная следующая попытка отменяется вместе с ним |
| Three reviews - owner undo | MT671 / DC | 1, 2, 3 | Последнее подтверждение, включая финальное, может отменить его автор; активная следующая проверка блокирует Undo |

Параметры `UndoApprovalMode / UndoActorMode / UndoActiveReviewMode` соответственно:
`0 / 1 / 0`, `1 / 1 / 1`, `2 / 0 / 0`. Значения описаны в
[документации политики](ACCESS_ADMINISTRATION.md#workflow-undo-policy).

Для ручной проверки выбраны отдельные сообщения:

| Сценарий | Сообщение | Филиал | Workflow |
|---|---|---|---|
| Один этап | `TEST-00001` | London | Single confirmation - no undo |
| Undo до начала второго этапа | `TEST-00002` | Dublin | Two confirmations - undo first |
| Undo во время второго этапа | `TEST-00005` | Singapore | Two confirmations - undo first |
| Финальное подтверждение двух этапов | `TEST-00008` | London | Two confirmations - undo first |
| Три этапа и Undo автора | `TEST-00003` | Singapore | Three reviews - owner undo |
| Блокировка Undo активной проверкой | `TEST-00006` | London | Three reviews - owner undo |
| Отклонение | `TEST-00014` | Singapore | Two confirmations - undo first |

## Общие правила прохождения

- Выберите **All** и найдите сообщение по **External ID**. После смены состояния
  сообщение может исчезнуть из ранее выбранного фильтра.
- Назначающий пользователь нажимает **Assign**, выбирает проверяющего и подтверждает
  назначение. Обычный пользователь не может назначить сообщение самому себе.
- Проверяющий открывает **Review**. Это запускает попытку проверки. **View** только
  показывает содержимое и не меняет состояние.
- **Approve** завершает этап. После каждого подтверждения назначение снимается;
  перед следующим этапом требуется новое назначение.
- Один обычный пользователь не может подтвердить два разных этапа одного сообщения.
  Правила Undo не отключают это существующее ограничение.
- **Close** или крестик оставляет проверку активной. Для прекращения попытки нужно
  нажать **Cancel review**. Это действие сохраняет назначение.
- **Undo** требует отдельного подтверждения **Confirm undo**. Комментарий необязателен.
  При успешном Undo назначение снимается; для продолжения снова нужен **Assign**.
- Часть кнопок скрывается или блокируется правами и состоянием. Проверьте результат
  после **Refresh** и откройте аудит через **View audit trail**.

## Один этап без обычного Undo

Сообщение: `TEST-00001`. Пользователи: Theo и Amelia.

1. Theo назначает сообщение Amelia.
2. Amelia открывает **Review**. Ожидается `FirstReviewInProgress`.
3. Amelia вводит комментарий `Single step checked` и нажимает **Approve**.
4. После обновления ожидается `Completed`, исполнитель отсутствует.
5. У Amelia и Theo Undo недоступен, хотя у роли есть `review.undo`.
6. В аудите проверьте подтверждение от Amelia и снятие назначения.

## Отмена чужого первого подтверждения

Сообщение: `TEST-00002`. Пользователи: Theo и Priya.

1. Theo назначает первый этап Priya.
2. Priya открывает **Review** и нажимает **Approve** с комментарием `First confirmation`.
3. Ожидается `WaitingForSecondReview`, без исполнителя.
4. Theo обновляет свою очередь, нажимает **Undo**, вводит `Please recheck` и подтверждает.
5. Ожидается `Assigned`, без исполнителя. Первая попытка имеет статус `Undone`.
6. В аудите автор исходного подтверждения — Priya, исполнитель Undo — Theo.
   Исходный комментарий подтверждения сохранён, комментарий отмены записан отдельно.
7. Theo снова назначает сообщение Priya. Она может начать новую первую попытку:
   отменённое подтверждение не запрещает повторную проверку этого этапа.

## Отмена первого подтверждения во время второго этапа

Сообщение: `TEST-00005`. Пользователи: Theo, Priya и Lucas.

1. Theo назначает первый этап Priya; Priya выполняет **Review → Approve**.
2. Theo назначает следующий этап Lucas.
3. Lucas открывает **Review**, но не подтверждает. Состояние — `SecondReviewInProgress`.
   Оставьте окно открытым в его вкладке.
4. Theo обновляет очередь и нажимает **Undo**. Диалог должен предупредить, что активная
   следующая проверка также будет отменена. Нажмите **Confirm undo**.
5. Ожидается `Assigned` без исполнителя. Первая попытка — `Undone`, вторая — `Cancelled`.
   Аудит содержит отмену проверки, отмену подтверждения и снятие назначения от Theo.
6. В старом окне Lucas попробуйте **Approve**. Операция должна быть отклонена: попытка
   уже закрыта. Сообщение не должно стать `Completed`. Закройте окно и обновите таблицу.
7. Для продолжения Theo назначает первый этап заново.

## Завершение двух этапов и запрет обычного Undo

Сообщение: `TEST-00008`. Пользователи: Theo, Priya и Lucas.

1. Theo назначает первый этап Priya; Priya выполняет **Review → Approve**.
2. Убедитесь, что Priya нельзя выбрать проверяющей второго этапа: её первое подтверждение
   ещё действует. Theo назначает второй этап Lucas.
3. Lucas выполняет **Review → Approve**.
4. Ожидается `Completed`, оба подтверждения действуют, исполнитель отсутствует.
5. После обновления у Theo, Priya и Lucas Undo недоступен. Нельзя отменить ни первое,
   ни второе подтверждение.

## Три этапа и отмена последнего подтверждения автором

Сообщение: `TEST-00003`. Пользователи: Theo, Priya и Lucas.

| Этап | Кто назначает | Кто выполняет Review и Approve | Состояние после Approve |
|---|---|---|---|
| 1 | Theo | Priya | `WaitingForSecondReview` |
| 2 | Theo | Lucas | `WaitingForThirdReview` |
| 3 | Priya | Theo | `Completed` |

1. Пройдите три строки таблицы. На третьем этапе назначает Priya, потому что Theo
   не может назначить сообщение самому себе.
2. После завершения обновите вкладки. Undo доступен Theo — автору последнего подтверждения.
   Priya и Lucas не могут отменить чужое последнее или своё более раннее подтверждение.
3. Theo выполняет **Undo → Confirm undo**.
4. Ожидается `WaitingForThirdReview`, без исполнителя. Только третья попытка имеет
   статус `Undone`; первые две остаются `Approved`.
5. При необходимости Priya снова назначает третий этап Theo. Он может повторить его.

## Активная проверка блокирует отмену автора

Сообщение: `TEST-00006`. Пользователи: Theo, Priya и Lucas.

1. Theo назначает первый этап Priya; Priya выполняет **Review → Approve**.
2. Пока второй этап не начат, Undo доступен Priya, но недоступен Theo. Пока не отменяйте.
3. Theo назначает второй этап Lucas; Lucas открывает **Review**.
4. После обновления Undo у Priya недоступен: этот workflow блокирует отмену во время
   активной проверки. Простое закрытие окна Lucas не снимает блокировку.
5. Lucas нажимает **Cancel review**. Ожидается `WaitingForSecondReview`; назначение
   Lucas сохраняется, но попытка закрыта как `Cancelled`.
6. Priya обновляет очередь и выполняет **Undo → Confirm undo**.
7. Ожидается `Assigned`, без исполнителя. Первое подтверждение отменено, назначение
   Lucas закрыто. В аудите отмену второй попытки выполнил Lucas, а Undo — Priya.

## Административное исключение

Используйте `TEST-00008` после сценария завершения двух этапов.

1. Откройте очередь с `?user=admin` и найдите сообщение в `Completed`.
2. Undo доступен администратору, хотя обычные пользователи не могут отменять финальное
   подтверждение этого workflow.
3. Выполните **Undo → Confirm undo** с комментарием `Administrator exception`.
4. Ожидается `WaitingForSecondReview`, без исполнителя. Отменено подтверждение Lucas;
   первое подтверждение Priya сохранено. Аудит Undo указывает `admin`.

Исключение действует при отсутствии активной проверки. Во время активной проверки
администратор соблюдает политику её отмены: двухэтапный пример разрешает её отменить
вместе с первым подтверждением, трёхэтапный пример блокирует Undo до закрытия проверки.

## Ограничение области доступа

1. Откройте очередь под Amelia. `TEST-00001` должен быть виден независимо от того,
   прошли ли вы сценарий его подтверждения.
2. `TEST-00002`, `TEST-00005` и `TEST-00003` не должны быть доступны Amelia:
   они находятся вне London / CS. Наличие `review.undo` не расширяет область доступа.
3. Theo видит все эти сообщения благодаря своим назначениям роли во всех областях.
4. Amelia не должна получать доступ к странице администрирования. `admin` получает его.

## Отклонение сообщения

Сообщение: `TEST-00014`. Пользователи: Theo, Priya и Lucas.

1. Theo назначает первый этап Priya; Priya выполняет **Review → Approve**.
2. Theo назначает второй этап Lucas; Lucas открывает **Review** и нажимает **Reject**.
3. Ожидается `Rejected`, исполнитель отсутствует. В аудите отклонение записано от Lucas.
4. Undo недоступен всем, включая `admin`. Повторное открытие через Undo не поддерживается.
   Содержимое и аудит доступны для просмотра.

## Как повторять проверки

Для нового прохода выбирайте другое сообщение с тем же типом и подходящей областью
доступа либо заново загружайте seed в отдельную тестовую БД. Повторная загрузка удалит
результаты всех предыдущих сценариев. После неё обновите страницы: внутренние ID будут
новыми, а номера `TEST-xxxxx` останутся прежними.

Если результат отличается, проверьте пользователя в текущей вкладке, фильтр таблицы,
текущее назначение, действующие подтверждения и аудит. Важное различие: **Cancel review**
закрывает активную попытку и сохраняет назначение; **Undo** отменяет подтверждение
и снимает назначение.
