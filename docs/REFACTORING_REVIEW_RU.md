# SwiftReview: проверка архитектуры и план рефакторинга

Дата: 5 сентября 2026. Базовый commit: `4368c09`.

Решение имеет разумную основу: разделение Domain / Application / Infrastructure / API, явные use-case handlers, EF Core, Stateless, FluentValidation, типизированные frontend-контракты. Переписывать архитектуру не требуется. Главный риск — расхождение правил между назначением, активной проверкой и интерфейсом. Ниже три воспроизведённых дефекта, три адресных улучшения сопровождения и один условный кандидат на замену библиотекой.

Проверены backend, frontend, SQL-миграции и регистрация сообщений, фоновое назначение, legacy-host, генератор контрактов и существующие тесты. Это инженерное ревью текущего кода, а не сертификация по «всем стандартам»: нагрузочные испытания, аудит уязвимостей зависимостей, production-аутентификация и полная браузерная проверка доступности в него не входили. На этапе первоначального ревью рабочий код не изменялся; статусы ниже отражают последующие исправления.

## Приоритеты

| ID | Приоритет | Кейс | Основание | Объём |
| --- | --- | --- | --- | --- |

P1 — исправить в ближайшем цикле: штатная операция оставляет пользователю невыполнимую работу. P2 — адресный следующий этап. P3 и L1 — выполнять при доказанном сокращении сложности. Оценки относительные, без обещания календарных сроков.

## R1. Общие правила пригодности проверяющего для ручного и автоматического назначения

**Статус:** исправлено после ревью. Ручное и автоматическое назначение используют общий расчёт уровня, permission и списка пользователей с действующим `Approved`; добавлены регрессионные тесты для `Approved` и `Undone`.

**Код:** [AssignMessageHandler](../backend/src/ORP.Application/Assignments/Assign/AssignMessageHandler.cs#L19), [AutomaticAssignmentService](../backend/src/ORP.Application/Assignments/Automatic/AutomaticAssignment.cs#L35), [AutomaticAssignmentQueries](../backend/src/ORP.Infrastructure/Persistence/AutomaticAssignmentQueries.cs#L20), [Message.StartReview](../backend/src/ORP.Domain/Messages/Message.cs#L32).

Автоматическое назначение исключает пользователей, уже подтвердивших предыдущие уровни. Ручное назначение проверяет права и область доступа, но не историю подтверждений. Поэтому оно может успешно назначить пользователя, которому four-eyes запрещает начать следующий уровень.

Воспроизведено на отдельном экземпляре API с mock data и отключённым worker:

| Сообщение 2, последовательность | Пользователь | Ответ |
| --- | --- | --- |
| `assign {assignedTo: 2}` | admin | 204 |
| `reviews/start {level: 1}` | theo.mercer | 201 |
| `reviews/approve {level: 1}` | theo.mercer | 204 |
| `reassign {assignedTo: 2}` | admin | 204 |
| `reviews/start {level: 2}` | theo.mercer | 403 |

Это не обход four-eyes: запрет срабатывает. Дефект в том, что система принимает заведомо непригодное назначение и требует дополнительного вмешательства.

**Минимальное изменение:** загрузить историю до ручного назначения и применить ту же проверку предыдущих подтверждений. При этом выделить небольшой общий расчёт требуемого уровня/права и исключённых reviewer IDs, используемый обоими путями. Сохранить SQL-фильтрацию кандидатов; не загружать всех пользователей в память ради одной C#-функции. Для SQL и доменной части зафиксировать одинаковые примеры пригодности тестами.

**Готово, когда:** пользователь с предыдущим `Approved` отклоняется до записи assignment и audit; пользователь с `Undone` остаётся допустимым; сохраняются проверки branch/department/permission. Не превращать это в универсальный rules engine.

## R2. Развести ответственность за сообщение и владение активной проверкой

**Статус:** исправлено после ревью с сохранением текущей доменной семантики. Read model содержит ID, уровень и reviewer активной проверки; `mine` включает текущего assignee и владельца active review; UI показывает владельца и разрешает Approve активной проверки только ему. Добавлены query-, frontend- и сквозной API-тесты переназначения.

**Код:** [Message.Assign](../backend/src/ORP.Domain/Messages/Message.cs#L25), [ApproveReviewHandler](../backend/src/ORP.Application/Reviews/ReviewHandlers.cs#L60), [AssignedMessagesPage](../frontend/src/pages/messages/AssignedMessagesPage.tsx#L68), [canReviewMessage](../frontend/src/pages/messages/reviewDecision.ts#L29), [MessageGridRowDto](../backend/src/ORP.Infrastructure/Persistence/MessageGridQueries.cs#L10).

`Reassign` меняет `CurrentAssigneeId`, сохраняя `Review.ReviewerId`. Approve разрешён только автору активной проверки. UI показывает действия только в `scope=mine`, а видимость Approve определяет по состоянию и permission; сведений об активном reviewer в строке нет.

Воспроизведено: admin начал уровень 2 сообщения 3, затем переназначил его victor.stone. Переназначение вернуло 204. Victor получил 409 `Only the reviewer who started the review can approve it.` Прежний reviewer — admin — всё ещё успешно подтвердил уровень через API, хотя сообщение уже не относится к его `mine`.

Текущая серверная семантика прямо описана в [MESSAGE_STATE_MACHINE.md](../backend/docs/MESSAGE_STATE_MACHINE.md). Поэтому механическое изменение reviewer при переназначении будет изменением бизнес-правил, а не безопасным рефакторингом. Аналогично, `StartReview` сейчас не требует совпадения reviewer и assignee; `Reject` намеренно разрешён не только автору проверки. Не добавлять эти запреты автоматически.

**Предпочтительный вариант с сохранением правил:** явно представить активную проверку в модели чтения — её ID, уровень и reviewer ID. Дать прежнему reviewer доступ к его незавершённым проверкам независимо от списка назначений; новый ответственный должен видеть, кто ведёт проверку. Вычисление доступных действий держать в одном месте на backend, если для него уже требуются история и правила доступа. UI использует результат для отображения, а команда повторно проверяет права и состояние при выполнении.

**Более простой вариант, если передача активной работы не нужна:** запретить переназначение в `*ReviewInProgress` с понятным конфликтом. Это продуктовый выбор, который нужно зафиксировать перед реализацией. Передача самой проверки с отдельным событием истории — более дорогая альтернатива; не включать её по умолчанию.

**Готово, когда:** после любого допустимого переназначения понятно, кто может завершить активный уровень и где он находит эту работу; UI не предлагает новому assignee невозможный Approve. Проверить сценарий целиком через API и браузер, включая историю и конкурентное переназначение. Моки кнопок не проверяют этот контракт.

## R3. Ограничить конфигурацию workflow возможностями машины состояний

**Статус:** исправлено после ревью. Активный workflow теперь обязан иметь хотя бы один обязательный уровень, начинаться с обязательного уровня 1 и перечислять обязательные уровни по возрастанию. Инвариант проверяется при активации, сохранении и использовании конфигурации; новая миграция проверяет существующие данные и защищает SQL-регистрацию сообщений. Пропуск optional level 2 между обязательными уровнями 1 и 3 сохранён.

**Код:** [WorkflowDefinition.AddStep / RequiredLevels](../backend/src/ORP.Domain/Workflows/WorkflowDefinition.cs#L28), [ORPDbContext](../backend/src/ORP.Infrastructure/Persistence/ORPDbContext.cs#L48), [ValidateWorkflowConfiguration](../backend/src/ORP.Infrastructure/Persistence/Migrations/20260905210000_ValidateWorkflowConfiguration.cs), [AssignNewMessageHandler](../backend/src/ORP.Application/Assignments/Automatic/AutomaticAssignment.cs#L60).

`AddStep` проверяет диапазон и уникальность, но допускает optional level 1 с обязательным level 2 и произвольный порядок уровней. Автоназначение выбирает первый обязательный уровень. При этом `Assigned → StartReview` всегда переводит сообщение в `FirstReviewInProgress`, а API считает `Assigned` состоянием для уровня 1.

Исполняемый доменный пример:

```csharp
var workflow = new WorkflowDefinition("Optional first", "MT199", 1)
    .AddStep(1, 1, false)
    .AddStep(2, 2);
var message = new Message(1, workflow.Id);
message.Assign(2);
var review = message.StartReview(2, 2, workflow, [], DateTimeOffset.UtcNow);
// review.Level == 2; message.State == FirstReviewInProgress
```

Через HTTP такой старт уровня 2 остановит authorization ещё в `Assigned`. Через домен получается несогласованная пара состояния и уровня. В текущих seed-конфигурациях первый уровень обязателен: это дефект допустимой конфигурации, а не утверждение о повреждённых production-данных.

**Минимальное изменение:** если продукт поддерживает стандартные возрастающие уровни, валидировать завершённую конфигурацию: первый обязательный уровень — 1, обязательные уровни идут по возрастанию, обязательных шагов хотя бы один. Допустимый пропуск optional level 2 между 1 и 3 сохранить. Проверять конфигурацию на границе записи/активации и до использования настроек из БД; EF-материализация не вызывает `AddStep`. При SQL-управлении справочником предусмотреть проверку в пути публикации настроек.

Если первый обязательный уровень 2/3 действительно нужен, потребуется согласованно изменить доменные переходы, authorization, назначения и frontend. Не строить динамический workflow engine без такого требования.

**Готово, когда:** неподдерживаемая конфигурация отклоняется до регистрации/назначения работы; стандартные 1, 1→2, 1→2→3 и допустимые optional-шаги проходят тесты; состояние активной проверки соответствует её уровню.

## R4. Один контекст выполнения операции вместо повторной загрузки на границе API/Application

**Код:** [ApiEndpoints.AuthorizationResource](../backend/src/ORP.Api/Endpoints/ApiEndpoints.cs#L96), [ReviewHandlers.LoadAsync](../backend/src/ORP.Application/Reviews/ReviewHandlers.cs#L44), [ReassignMessageHandler](../backend/src/ORP.Application/Assignments/Reassign/ReassignMessageHandler.cs), [UserAccessService](../backend/src/ORP.Infrastructure/Identity/UserAccessService.cs#L9).

Endpoint загружает message, source и reviews для authorization, после чего review handler повторно запрашивает message и reviews, добавляя workflow. `Reassign` дополнительно читает message в обёртке и снова в Assign handler. `SingleOrDefaultAsync` выполняет запрос и для уже отслеживаемой сущности: identity resolution не устраняет обращение к БД. Для read-запросов debug authentication и handler также повторно загружают доступ текущего пользователя через `AsSplitQuery`.

Проблема не в длине `ApiEndpoints.cs`: загрузка контекста и правила выполнения распределены между transport и use case. Read handlers сами получают доступ пользователя, а write handlers полагаются на предварительную авторизацию endpoint. В текущих HTTP-маршрутах проверки есть; обход доступа через действующий маршрут не обнаружен. Но повторное использование write handler требует знания этого неявного предусловия.

**Изменение:** собрать загрузку и авторизацию интерактивной команды в одну явную application-границу. Небольшой контекст операции содержит необходимые message/source/workflow/reviews и actor access; после проверки его использует операция, затем выполняется один `SaveChangesAsync`. ASP.NET-адаптер отвечает за аутентификацию и преобразование результата в HTTP. Системный `AssignNewMessageHandler` сохраняет отдельную точку входа.

Практически начать с одного review-сценария. Общие `LoadAsync` и создание audit больше не должны принадлежать `StartReviewHandler`, от которого зависят остальные handlers: использовать предметный загрузчик и существующий `AuditEventFactory`. Не создавать общий базовый handler или pipeline ради этих двух функций. Доступ actor допустимо переиспользовать в пределах запроса; межзапросный кеш прав без правил отзыва доступа не нужен.

**Готово, когда:** авторизация выполняется до изменений, application-вход проверяется без ASP.NET, сохраняются действующие правила 403/404, один контекст не загружается повторно, транзакция охватывает состояние, review, assignment и audit. Снижение числа SQL-команд подтвердить логом/перехватчиком для одного сценария; ускорение без измерений не обещать.

## R5. Единая нормализация HTTP-ответов и ошибок

**Код:** [client.ts](../frontend/src/shared/api/client.ts#L41), [referenceDataApi.ts](../frontend/src/shared/api/referenceDataApi.ts#L15), [messagesApi.ts](../frontend/src/pages/messages/messagesApi.ts#L15), [ReviewDecisionPopup](../frontend/src/pages/messages/ReviewDecisionPopup.tsx#L58).

Часть API использует `apiClient.GET` с `{data, response}`, часть — `apiFetch` с ручным разбором ответа. `postReviewAction` отдельно читает Problem Details только для 409. Справочники и audit сохраняют отмену по signal, а `getMessage` оборачивает её в обычный `Error`. `ApiError` сохраняет только status; доступный `X-Correlation-ID` теряется. Для одного изменения политики ошибок приходится править несколько независимых реализаций.

**Изменение:** один небольшой transport helper для JSON/204 и один разбор неуспешного ответа в существующий `ApiError` с status, допустимыми деталями и correlation ID. Отмену сохранять как отмену. Локальные API-функции задают endpoint, payload и тип; компоненты выбирают понятный текст по контексту операции. Не добавлять Axios только ради замены `fetch`.

Реализовать ограниченный первый этап уже существующего [ERROR_HANDLING_PLAN.md](../frontend/docs/ERROR_HANDLING_PLAN.md), а не параллельный проект глобальных toast/telemetry. Сейчас 409 с причиной отсутствия следующего reviewer полезен пользователю; это поведение сохранить. Сетевые ошибки команд не повторять автоматически: результат записи может быть неизвестен.

**Готово, когда:** JSON, 204, 400/403/409/500, пустое/невалидное тело ошибки и отмена обрабатываются одинаково; исходный HTTP status не теряется при ошибке разбора. Повторы TanStack Query сохраняют текущую политику. Загрузка грида остаётся `CustomStore → DevExtreme.AspNet.Data`; общий transport не переносит её в Query.

## R6. Отделить оболочку audit drawer от грида и истории

**Код:** [MessagesGrid](../frontend/src/pages/messages/MessagesGrid.tsx#L123), [AuditTrailDrawer](../frontend/src/pages/messages/AuditTrailDrawer.tsx#L121).

Грид управляет portal, Escape, `inert` корневого элемента и возвратом фокуса. Содержимое истории отдельно реализует focus trap, поиск focusable-элементов и глобальный `focusin`. Жизненный цикл одного модального окна распределён между таблицей и представлением audit. Это конкретная SRP-проблема: изменение оболочки затрагивает два компонента с предметными обязанностями.

**Изменение:** сначала проверить использование уже установленного DevExtreme `Popup`, оформленного как правая панель. У него предусмотрены container/position/shading и управление циклом Tab; пригодность для текущего drawer нужно проверить в браузере. [Документация DevExtreme Popup](https://js.devexpress.com/React/Documentation/ApiReference/UI_Components/dxPopup/).

Грид должен выбирать сообщение, отдельная оболочка — управлять открытием/закрытием, содержимое — показывать историю и её загрузку. Не создавать универсальный modal manager. Если Popup требует больше обходного кода или меняет необходимый UX, сохранить Drawer и перенести его связанную DOM-механику в одну конкретную оболочку.

**Готово, когда:** проверены Escape, Tab/Shift+Tab, возврат фокуса, повторное открытие, пагинация и reduced motion; после unmount нет оставшегося `inert` или обработчиков. Удаляется собственная механика либо явно уменьшается число её владельцев. Нарушение WCAG здесь не заявляется: браузерная проверка в этом ревью не проводилась.

## L1. Библиотека вместо собственного OpenAPI-парсера — только после сравнения

**Код:** [OpenApiSchemaParser](../tools/OpenApiTsContracts/OpenApi/OpenApiSchemaParser.cs), [TypeScriptTypeResolver](../tools/OpenApiTsContracts/Generation/TypeScriptTypeResolver.cs), [README генератора](../tools/OpenApiTsContracts/README.md).

Только `OpenApi/` и `Generation/` содержат 1241 строку; парсер — 741. Инструмент поддерживает собственное подмножество стандарта и намеренно отклоняет многие композиции схем. Появление такого контракта потребует расширения отдельного парсера, модели и тестов. Здесь библиотека потенциально устраняет значимый пласт сопровождения, а не заменяет несколько строк.

Кандидат — devDependency `openapi-typescript`: генерирует TypeScript-типы из OpenAPI 3.0/3.1 без runtime-кода, поддерживает discriminator. [Официальная документация](https://openapi-ts.dev/introduction).

Но существующий генератор работает, имеет 58 проходящих тестов, детерминированный вывод, namespace-фильтрацию и явные правила отказа. Текущий OpenAPI успешно проходит `--check`. Замена не является обязательным исправлением.

**Эксперимент:** на сохранённом текущем OpenAPI и fixture сравнить required/optional/null, enum, dictionaries и references. Проверить импорт типов через `components["schemas"]`, стоимость перехода существующих DTO-импортов и необходимость namespace-фильтра. Сохранить проверку актуальности контрактов без изменения рабочего дерева. Если нужны десятки адаптеров для прежнего формата или строгие отказы парсера являются требованием продукта, оставить текущий инструмент. Если общий код действительно удаляется — мигрировать отдельным PR. Устанавливать библиотеку до сравнения в основной проект не требуется.

## Что сохранить и что отложить

| Область | Решение |
| --- | --- |
| Domain / Application / Infrastructure | Сохранить направление зависимостей. Domain не зависит от API/EF; использование Stateless оправдано переходами и тестами. |
| Handlers и DI | Сохранить прямой вызов handlers. MediatR, базовые классы и интерфейс на каждый handler не решают найденные проблемы. |
| `IORPStore` / EF Core | Текущий интерфейс достаточно предметный. Generic repository, дополнительный Unit of Work и дробление по одному методу не нужны. |
| Транзакция approval + auto-assignment | Сохранить. Отказ при отсутствии следующего reviewer — документированное и протестированное правило. Перенос в очередь/outbox поменяет поведение. |
| DevExtreme grid | Сохранить серверные фильтрацию/пагинацию, whitelist полей, лимиты фильтра и `CustomStore`. Связь grid endpoint с конкретным Infrastructure query сама по себе не основание для нового слоя. |
| SQL и concurrency | Сохранить rowversion, уникальное активное назначение, append-only audit. Тест с SQL Server уже существует и проходит. |
| React state | TanStack Query для обычных серверных данных и локальный state для диалогов достаточны. Redux/Zustand не обоснованы. |
| Размер файлов и оформление | Не заводить задачи на короткие строки, порядок `using`, число record в файле, переименование или механическое дробление endpoints. |
| Bundle | Build предупреждает о крупных chunks: initial JS около 337 КБ gzip, grid chunk около 381 КБ gzip, CSS около 106 КБ gzip. Lazy routes уже есть. Решение об оптимизации принять после измерения времени открытия основных экранов на целевых устройствах. Само предупреждение не доказывает проблему UX. |

Отдельные незавершённые интеграции уже обозначены в репозитории: вне Development debug authentication отклоняет вход, production-схема пока не подключена; `LegacySwiftSynchronizer.Run` намеренно завершается ошибкой до подключения пакета; начальный `SwiftMessageSource` — пустая bootstrap-view. Это задачи интеграции перед deployment, а не основания рефакторить рабочую архитектуру. Режим Development не является способом включения production-аутентификации.

## Последовательность изменений

1. **Выполнено — R1:** общий критерий пригодности и регрессионный тест ручного назначения предыдущему reviewer. Без перестройки handlers.
2. **Выполнено — R2:** сохранено владение active review исходным reviewer, согласованы API/read model/UI, добавлен сквозной сценарий переназначения.
3. **Выполнено — R3:** проверка поддерживаемых workflow-конфигураций в домене, EF и SQL-регистрации; миграция останавливается при несовместимых активных данных; добавлены тесты активации, optional/order и SQL Server.
4. **PR 4 — R4:** один контекст для выбранного write use case, затем перенос других операций по тому же простому шаблону. Доказать сохранение authorization, atomicity и concurrency на SQL Server.
5. **PR 5 — R5:** общий разбор ответов и ошибок; сохранить контекстные сообщения и независимость grid loader.
6. **R6/L1:** отдельные небольшие изменения только при подтверждённом выигрыше. Их выполнение не должно задерживать P1.

Дополнительные тесты прежде всего должны закрывать R1–R3, а не зеркально проверять каждый новый helper. Существующий большой SQL end-to-end тест полезно дополнять независимыми сценариями с общей SQL fixture: падение раннего assert сейчас прекращает проверки ниже в том же тесте. Саму InMemory-базу оставить для mock mode и быстрых проверок; SQL-specific семантику проверять на SQL Server. Это соответствует [рекомендациям EF Core о выборе стратегии тестирования](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy).
