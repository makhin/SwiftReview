# SwiftReview: тест-план и тест-кейсы

Дата последнего прогона: **18 октября 2026 года**.

## Цель и границы

Проверить пользовательские сценарии frontend совместно с API и SQL Server: таблицы сообщений, назначения, подтверждения и review, права доступа, администрирование, PDF, аудит и адаптивный интерфейс. Сохранение считается успешным только после проверки состояния на сервере.

Это набор регрессионных сценариев, а не утверждение о покрытии всех возможных комбинаций данных и прав. Backend и HTTP-контракты при последнем прогоне не менялись.

Обозначения в результатах кейсов:

- **Live UI** — браузер с настоящими API и SQL Server.
- **Live API** — HTTP-запросы к настоящему API с проверкой ответа и сохранённого состояния.
- **Fixture UI** — production-сборка и реальные UI-компоненты с контролируемыми HTTP-ответами; эта проверка не подтверждает интеграцию с SQL Server.
- **Не проверено** — сценарий включён в план, но свидетельств его выполнения в последнем прогоне нет.

## Подготовка и порядок выполнения

1. Проверить рабочее дерево и настройки выбранного окружения. Следовать [инструкциям репозитория](../AGENTS.md), [описанию API](API.md) и [сценариям тестовых данных](TEST_DATA_SCENARIOS_RU.md).
2. В подготовленном Docker-окружении запустить `./run-dev.docker.sh`. Пароль SQL получать из окружения или только из ключа `MSSQL_SA_PASSWORD` в игнорируемом `backend/.env`; не выводить его и не исполнять dotenv как shell-код. Ожидаемые адреса: frontend `http://localhost:5173`, API `http://localhost:5080`.
3. Не сбрасывать постоянную dev-базу. Для сценариев, меняющих сообщения, права и роли, использовать отдельную тестовую базу с известными данными. Перед началом записать исходные назначения, состояния и права.
4. Подготовить администратора, трёх разных проверяющих с подходящими правами и областями доступа, пользователя без бизнес-доступа и неизвестную identity. Переключение через `?user=...` и `X-Debug-User` применять только в Development.
5. Подготовить отдельные сообщения для single/double confirmation, review с двумя и тремя уровнями, rejection, undo, смены workflow и просмотра. Для списка нужны данные минимум на две страницы. Не использовать один уже изменённый кейсом объект как свежую предпосылку другого кейса.
6. Выполнить автоматические наборы, затем live-кейсы. Записывать фактические результаты, состояние до/после и способ проверки. Ожидаемые отказы 401/403/409 отличать от неожиданных ошибок.
7. Удалить только созданные для прогона временные ресурсы. Убедиться, что исходная dev-база не изменена тестовыми действиями.

Docker-launcher, Docker solution и часть SQL-проверок локальные и игнорируются Git: в обычном clone они могут отсутствовать. Для Windows/external SQL использовать инструкции соответствующего окружения; не запускать Docker автоматически.

### Команды проверок

Из корня репозитория, в подготовленном локальном Docker-окружении:

```sh
./test-backend.docker.sh -m:1
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend run test:smbc
git diff --check
```

`test:smbc` уже выполняет production build. Отдельная команда сборки: `npm --prefix frontend run build`. Браузерные проверки находятся в [check-smbc.mjs](../frontend/scripts/check-smbc.mjs) и [check-unsaved-changes.mjs](../frontend/scripts/check-unsaved-changes.mjs).

Для браузерного регрессионного прогона не использовать повторный запуск после падения как основание для PASS. После исправления причины проводить новый явно обозначенный прогон. Циклы многократного открытия/отмены диалога являются шагами теста, а не retry.

## Критерии завершения следующего прогона

- Для каждого применимого кейса записаны PASS/FAIL/не выполнено, окружение и способ проверки.
- Изменения бизнес-состояния подтверждены серверным чтением; отказы не изменяют состояние.
- Применимые автоматические наборы проходят; браузерный результат не скрывает flaky-падения повторными запусками.
- Нет необъяснённых ошибок UI/API; известные ограничения и пропущенные проверки перечислены отдельно.
- Постоянная dev-база сохранена, временные ресурсы очищены.
