# Оценка предложений по конфигурации workflow

Оценка от 30 сентября 2026 года по трём предоставленным фотографиям предложения.
Документ сопоставляет предложенные настройки с текущей реализацией и
[сводными бизнес-требованиями](CONSOLIDATED_BUSINESS_REQUIREMENTS.md).
Это архитектурная рекомендация, а не согласованный план реализации новых функций.

В предложении есть полезные настройки, закрывающие реальные пробелы приложения.
Однако полная схема одновременно вводит выбор процесса, правила проверки,
версионирование, согласование конфигурации и универсальную автоматизацию.
Рекомендуется внедрять подтверждённые правила по отдельности; необходимость всего
конструктора процессов пока не обоснована.

## Что означает направление сообщения

Направление определяется относительно банка:

- `Incoming` — банк получил SWIFT-сообщение.
- `Outgoing` — банк отправил SWIFT-сообщение.

Это характеристика сообщения, а не направление перехода между этапами workflow.
Один тип сообщения может обрабатываться по-разному в зависимости от направления.
Например, входящее сообщение может требовать двух подтверждений, а исходящее — одного.
Это иллюстрация: конкретную матрицу типов, направлений и числа подтверждений необходимо
согласовать. В требованиях расширенного TFO такие различия пока отмечены как предварительные.

Направление теперь представлено общим enum `MessageDirection`: `Incoming = 1`,
`Outgoing = 2`. В БД хранится `int`, в API — имя enum. Направление workflow обязательно;
отсутствующее направление исходного сообщения не считается Incoming.

[WorkflowResolver](../backend/src/ORP.Infrastructure/Persistence/WorkflowResolver.cs)
учитывает тип сообщения, направление, подразделение и филиал. Конкретный филиал
имеет приоритет над общим правилом внутри того же направления. При ручной смене
workflow направление должно совпадать, включая действия администратора.

## Полезные идеи

| Предложение | Польза и рекомендуемый подход |
|---|---|
| `direction` | Учитывать направление при выборе workflow, когда подтверждена соответствующая бизнес-матрица. Подразделение и приоритет конкретного филиала сохраняются. |
| `distinctUserRequired` | Отделить число подтверждений от требования разных проверяющих. Для текущих требований достаточно настройки на уровне workflow. |
| Версия применённых правил | Сохранять правила, по которым обрабатывается уже начатое сообщение. Изменение настройки не должно неожиданно менять его процесс. |
| Поведение при Reject | Для TFO описан возврат после второго подтверждения. Это основание для отдельной настройки после уточнения состояния, назначения и истории при возврате. |
| Названия этапов и примечания | Улучшают понимание процесса пользователями и сопровождение конфигурации. Стоимость реализации невелика. |
| Единственное подходящее правило | Предотвращает неоднозначный выбор процесса. Нужны корректный ключ области и явный приоритет общего и филиального правил. |

`id`, `policyKey` и `version` не обязательно дублируют друг друга: они могут обозначать
конкретную запись, семейство версий и номер версии. Полезность этих идентификаторов
нужно отделять от необходимости полноценного процесса согласования конфигурации.

## Что отложить или убрать из первой реализации

| Элемент | Оценка |
|---|---|
| `Draft → PendingApproval → Active → Retired` и второй администратор | Отдельный процесс управления изменениями с интерфейсом, правами и аудитом. Добавлять при явном требовании согласования конфигурации. |
| `effectiveFrom` и `effectiveTo` | Нужны для отложенной активации. Потребуют правил пересечения периодов и обработки уже поступивших сообщений. Пока достаточно явной активации. |
| `slaMinutes`, который пока не используется | Убрать до появления работающего SLA с правилами отсчёта времени и уведомлениями. Поле само по себе не реализует возможность. |
| `maxReturns = 3` | Вводит неподтверждённое правило окончательного закрытия после нескольких возвратов. Сам возврат и ограничение его количества требуют отдельных решений. |
| `External` с автоматической фиксацией выполнения | Внешняя проверка требует источника результата и свидетельства выполнения. Отсутствие проверки в приложении не доказывает её успешное завершение. |
| Универсальные `actions[]`, триггеры и `paramsJson` | Откладывать до появления нескольких конкретных сценариев автоматизации. Генерацию PDF можно реализовать как конкретное действие с нужной обработкой ошибок. |

Механизм автоматических действий потребует валидации параметров, повторных попыток
и защиты от повторного выполнения внешнего действия. Строка JSON внутри JSON
дополнительно усложняет проверку конфигурации. Потребность в PDF подтверждена, но она
сама по себе не обосновывает универсальные триггеры печати, экспорта и маршрутизации.

## Проблемы и неоднозначности показанной схемы

1. **Количество глаз не равно числу этапов, умноженному на два.** Если один человек
   может выполнить оба этапа, два подтверждения не означают независимую проверку двумя
   людьми. В интерфейсе лучше показывать число подтверждений и отдельное требование
   разных проверяющих; `eyes` не нужен как независимая настройка.
2. **Для TFO на фото задано `distinctUserRequired: true`, тогда как требования допускают
   одного пользователя на обоих этапах.** Текущая реализация также запрещает повторное
   участие обычного пользователя. Это реальный пробел, который изменение Undo не решает.
3. **В описанном ключе уникальности `messageType + branchCode + direction` нет подразделения.**
   Правила разных подразделений для одинаковых сообщений могут конфликтовать.
4. **`assigneeRole: "TFO"` смешивает подразделение и роль.** У нас уже есть права в точной
   паре филиал/подразделение. Независимая система назначения по строковому названию роли
   может расходиться с действующей авторизацией. Отдельный филиал исполнителя нужен,
   только если подтверждена обработка сообщений сотрудниками другого филиала.
5. **Требование разных пользователей на каждом этапе допускает неоднозначные комбинации.**
   Настройка на уровне workflow проще, пока нет подтверждённого требования к смешанным
   правилам внутри одного процесса.
6. **`NotRequired` и `External` имеют разный смысл.** Пропущенная проверка не является
   успешным внешним подтверждением; смешивать их статусы и аудит нельзя.
7. **В показанной части нет явной политики Undo.** Предложенная схема не заменяет наши
   настройки отмены подтверждений без дополнительного определения их поведения.

## Что взять в нашу модель

Рекомендуемые самостоятельные изменения:

- Направление добавлено в выбор workflow. Производственную матрицу этапов для каждого направления ещё нужно подтвердить.
- Добавить настройку разных проверяющих на уровне workflow. Применять её согласованно
  при выборе кандидатов, назначении, авторизации, начале проверки и расчёте кнопок таблицы.
- Отдельно реализовать согласованное поведение возврата при Reject с сохранением истории.
- Обеспечить неизменность применённых правил для уже начатых сообщений.
- Сохранить существующие scoped permissions и
  [политику Undo](ACCESS_ADMINISTRATION.md#workflow-undo-policy).

Для первого варианта версионирования достаточно принципа: изменённые правила получают
новую запись, а существующие сообщения сохраняют ссылку на прежнюю. Полный процесс
согласования конфигурации для этого необязателен. При этом нужно разделить доступность
workflow для новых сообщений и возможность продолжать уже начатые: сейчас `IsActive`
используется и при выборе, и при выполнении действий. Простое отключение старой записи
может остановить связанные с ней сообщения.

Generic-решение должно позволять нескольким workflow использовать общую проверенную
логику без условий по названиям подразделений. Универсальный язык описания всех будущих
процессов, интеграций и автоматических действий пока не требуется.
